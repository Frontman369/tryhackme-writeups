# TakeOver

## Overview

This challenge revolves around **subdomain / virtual host enumeration**.

The key lesson is recognizing when a target is using **name-based virtual hosting** and knowing when to use **Host header fuzzing** instead of traditional directory enumeration.

---

## 1. Configure `/etc/hosts`

The challenge provides the target machine IP:

```text
10.49.181.248
```

The first step is to map the challenge hostname to that IP address in `/etc/hosts`:

```bash
echo "10.49.181.248 futurevera.thm" | sudo tee -a /etc/hosts
```

Verify that the entry was added:

```text
10.49.181.248 futurevera.thm
```

This allows the local machine to resolve `futurevera.thm` to the TryHackMe lab machine.

Without this mapping, attempting to access:

```text
https://futurevera.thm/
```

will not reach the intended target.

---

## 2. Initial Enumeration

I initially tried Nmap, but it did not provide much information that helped with the actual challenge.

The room itself gives an important clue:

> This challenge revolves around subdomain enumeration.

That suggested that the interesting part of the target was likely its **virtual host configuration**, rather than simply its exposed directories.

Instead of focusing on directory enumeration, I switched to **Host header fuzzing**.

---

## 3. Establishing a Baseline Response

Before fuzzing, I wanted to determine what the server returned when supplied with a hostname that should not exist.

I sent an intentionally invalid Host header:

```bash
curl -I -k -H "Host: randomname.futurevera.thm" https://10.49.181.248
```

The server responded:

```text
HTTP/1.1 200 OK
Date: Fri, 28 Aug 2026 15:18:51 GMT
Server: Apache/2.4.41 (Ubuntu)
Last-Modified: Sun, 13 Mar 2022 08:48:57 GMT
ETag: "11fd-5da15a2613040"
Accept-Ranges: bytes
Content-Length: 4605
Vary: Accept-Encoding
Content-Type: text/html
```

The important value here is:

```text
Content-Length: 4605
```

So an invalid Host header produces a baseline response of **4605 bytes**.

This gives us something useful to filter when fuzzing. Rather than manually examining thousands of identical responses, we can tell ffuf to ignore responses matching that size.

---

## 4. Virtual Host Enumeration with ffuf

I used ffuf to fuzz the `Host` header:

```bash
ffuf -H "Host: FUZZ.futurevera.thm" \
     -u https://10.49.181.248 \
     -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-110000.txt \
     -fs 0,4605
```

The important part is:

```text
-H "Host: FUZZ.futurevera.thm"
```

This is **Host header fuzzing**.

We keep the target URL fixed while changing the hostname presented to the web server.

The `4605` response-size filter removes the baseline response generated by invalid virtual hosts.

### Results

Two interesting virtual hosts were discovered:

```text
support.futurevera.thm
blog.futurevera.thm
```

I added them to `/etc/hosts`:

```bash
echo "10.49.181.248 support.futurevera.thm blog.futurevera.thm" | sudo tee -a /etc/hosts
```

The entries were then:

```text
10.49.181.248 futurevera.thm
10.49.181.248 support.futurevera.thm
10.49.181.248 blog.futurevera.thm
```

## 5. A Wrong Turn: Directory Fuzzing

At this point, I made a mistake.

I started directory enumeration against the support subdomain:

```bash
ffuf -u https://support.futurevera.thm/FUZZ \
     -w /usr/share/wordlists/rockyou.txt
```

This produced a large number of false positives, many of which had a response size of approximately:

```text
1522 bytes
```

I attempted to filter them:

```bash
ffuf -u https://support.futurevera.thm/FUZZ \
     -w /usr/share/wordlists/rockyou.txt \
     -fs 0,1522
```

However, the scan was extremely large and was not proving useful, so I stopped it.

### Why was this the wrong approach?

The interesting attack surface was not necessarily a directory.

The challenge was centered around **virtual hosts**, meaning the server's behavior depends on the `Host` header.

Directory fuzzing changes the URL path:

```text
https://support.futurevera.thm/FUZZ
```

Host header fuzzing changes the virtual host:

```text
Host: FUZZ.futurevera.thm
```

These are two different enumeration techniques.

In this challenge, **Host header fuzzing was the relevant technique**.

This was an important lesson for me: always identify the attack surface before throwing a large wordlist at it.

## 6. Inspecting the Support Subdomain

Instead of continuing the directory scan, I went back to manual enumeration.

I first inspected the HTTPS service:

```bash
curl -v https://support.futurevera.thm
```

This produced a certificate-related error.

I then tried HTTP:

```bash
curl -v http://support.futurevera.thm
```

This returned a response.

The HTTP and HTTPS behavior appeared similar at first glance, but inspecting the certificate on the HTTPS service revealed something interesting.

The certificate contained a **Subject Alternative Name (SAN)** entry:

```text
DNS Name:
secrethelpdesk934752.support.futurevera.thm
```

That hostname immediately stood out as a potential clue.

---

## 7. Discovering the Secret Subdomain

I added the discovered hostname to `/etc/hosts`:

```bash
echo "10.49.181.248 secrethelpdesk934752.support.futurevera.thm" | sudo tee -a /etc/hosts
```

The important detail here is that I tested the hostname over **HTTP**:

```bash
curl -v http://secrethelpdesk934752.support.futurevera.thm
```

The response contained a redirect:

```text
Location: http://flag{beea0d6edfcee06a59b83fb50ae81b2f}.s3-website-us-west-3.amazonaws.com/
```

The flag is therefore:

```text
flag{beea0d6edfcee06a59b83fb50ae81b2f}
```

The redirect itself exposes the flag as part of the hostname.

---

## 8. Why HTTP Works but HTTPS Doesn't

Initially, I thought the reason was that the service only responded on port 80.

That assumption was incorrect.

Nmap shows that both HTTP and HTTPS are available:

```text
PORT    STATE SERVICE  VERSION
80/tcp  open  http     Apache httpd 2.4.41
443/tcp open  ssl/http Apache httpd 2.4.41
```

The actual explanation is related to **Apache virtual host configuration**.

The port 80 virtual host contains the rule responsible for the redirect:

```text
302 → S3
```

The HTTPS virtual host does not contain the same rule for the secret hostname.

As a result, requests behave differently depending on the protocol.

This can be verified with:

```bash
curl -sI http://secrethelpdesk934752.support.futurevera.thm
```

versus:

```bash
curl -skI https://secrethelpdesk934752.support.futurevera.thm
```

The HTTP request receives the redirect containing the flag, while the HTTPS request falls through to the HTTPS/default virtual host configuration instead.

### Why is this interesting?

The secret hostname was discovered from the SAN field of the HTTPS certificate, but the useful behavior was configured on the HTTP virtual host.

This is a good example of how differences between HTTP and HTTPS virtual-host configurations can expose unexpected behavior.

## 11. Lessons Learned

### Host Header Fuzzing vs Directory Fuzzing

One of my biggest mistakes was confusing two different enumeration techniques.

**Directory enumeration** looks for paths:

```text
https://target/FUZZ
```

**Virtual host enumeration** looks for different hostnames:

```text
Host: FUZZ.target
```

When a challenge specifically points toward subdomains or virtual hosts, Host header fuzzing should be considered early.

### Establish a Baseline Before Fuzzing

Before running a large ffuf scan, determine how the server responds to an invalid value.

In this case:

```bash
curl -I -k -H "Host: randomname.futurevera.thm" https://10.49.181.248
```

gave us a baseline response size of:

```text
4605
```

That allowed us to filter the noise from ffuf.

### Don't Ignore Certificates

Certificates are not only useful for encryption.

The SAN field can reveal additional hostnames that may not be obvious from other enumeration techniques.

In this challenge, the certificate revealed:

```text
secrethelpdesk934752.support.futurevera.thm
```

That hostname ultimately led to the flag.

### Test Both HTTP and HTTPS

Even when both ports are open, their virtual host configurations may behave differently.

A useful habit is to compare:

```bash
curl -I http://target
```

and:

```bash
curl -kI https://target
```

Differences in redirects, status codes, headers, and content can reveal configuration mistakes.

## 12. Personal Debrief

I did not solve this challenge perfectly on the first attempt.

I initially tried directory fuzzing against the support subdomain, which turned out to be the wrong attack surface. Rather than treating that as wasted effort, I used it as a reminder to step back and reconsider what the challenge was actually asking me to enumerate.

The important progression was:

**enumerate → observe → make a hypothesis → test it → recognize the mistake → change approach → verify the result.**

That is probably the biggest lesson I am taking from this challenge.

I started hunting for CTFs before finishing my learning path, and I expect to make mistakes like this. The goal is not to avoid every mistake—it is to recognize them faster and learn from them.

**With exposure comes expertise.**

I try. I fail. I fail harder.

And I get back up again.
